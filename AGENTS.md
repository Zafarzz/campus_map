# AGENTS.md — главный регламент работы AI-агентов

> **Обязательно к прочтению всем AI-агентам (Gemini, Claude и др.) перед началом любой работы в репозитории.**
> Этот документ определяет правила взаимодействия, границы ответственности и стандарты качества.
> Любой агент обязан строго следовать данному регламенту.

---

## 1. О проекте и его целях

Проект представляет собой интерактивную 3D-карту университетского кампуса (Ajou University in Tashkent).
Карта решает задачи визуальной навигации по зданиям и этажам, поиска аудиторий и отображения статуса занятости аудиторий по расписанию в реальном времени.

Текущее состояние кодовой базы:
- Полноценная внешняя 3D-геометрия корпусов, дорог и окружения.
- Приблизительные процедурные планировки помещений (коридоры и аудитории сгенерированы заглушками).
- Доступны чертежи в формате PDF с точными архитектурными планировками.

### Утверждённая последовательность этапов проекта
Порядок реализации строго фиксирован ([ADR-004](docs/DECISIONS.md#adr-004-фиксированная-последовательность-этапов-a--b--c)) и не подлежит изменению:
1. **Этап A — Точные планировки помещений**: перенос геометрии стен, комнат, коридоров и дверей из PDF в единый формат данных с сохранением соответствия расписанию и отображением в 3D.
2. **Этап B — 2D Edit Mode**: отдельный векторный режим редактирования карты сверху (добавление, удаление, перемещение корпусов, стен, дверей, комнат, привязка к сетке, Undo/Redo, валидация) с мгновенной синхронизацией с 3D.
3. **Этап C — Визуальное улучшение**: фотореалистичные материалы фасадов и кровли, естественное освещение, тени, детерминированное озеленение и благоустройство без потери производительности.

> [!IMPORTANT]
> Запрещено переходить к Этапу B до приёмки Этапа A. Запрещено переходить к Этапу C до приёмки Этапа B.

## 2. Фактический стек и ключевые точки входа

- **Сборка / Dev-сервер**: Vite `^8.3.3`, React `^19.3.0`, TypeScript `^7.0.2` (`strict: true`).
- **3D-графика**: Three.js `^0.186.1`, `@react-three/fiber` `^9.8.1`, `@react-three/drei` `^10.7.9`.
- **Тесты**: Vitest `^5.0.3` (команда `npm test`).
- **Проверка типов**: `npm run typecheck` (`tsc --noEmit`).
- **Ключевые точки входа**:
  - `index.html` → [`src/main.tsx`](src/main.tsx) — монтирование React-приложения.
  - [`src/App.tsx`](src/App.tsx) — компоновка `CampusMap` (3D) и панели интерфейса.
  - [`src/state/MapProvider.tsx`](src/state/MapProvider.tsx) — единый контекст данных, геометрии, выбора и времени.
  - [`src/services/geometry/index.ts`](src/services/geometry/index.ts) — единственная точка связывания данных с провайдером геометрии.

## 4. Золотые правила для AI-агентов (Gemini & Claude)

Каждый агент обязан следовать 10 ключевым правилам:

1. **Начинать работу с прочтения `AGENTS.md`** и профильного документа своего этапа.
2. **Не проводить аудит репозитория повторно**, если он уже зафиксирован в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md). Используйте существующие выводы.
3. **Соблюдать утверждённую спецификацию координат и данных** ([docs/GEOMETRY_SPEC.md](docs/GEOMETRY_SPEC.md)). Запрещено изобретать альтернативные системы осей или локальные форматы.
4. **Не создавать альтернативные архитектуры, форматы данных или дублирующие подсистемы.**
5. **Не менять публичные интерфейсы модулей без обновления документации** (см. границы изменений в [docs/ARCHITECTURE.md §8](docs/ARCHITECTURE.md#8-границы-изменений)).
6. **Не изменять решения со статусом `accepted`** в [docs/DECISIONS.md](docs/DECISIONS.md) без явного письменного обоснования и предложения нового ADR.
7. **Сообщать о конфликтах между документацией и кодом**, фиксируя их как открытый вопрос, вместо того чтобы самостоятельно выбирать трактовку.
8. **Изменять только файлы, относящиеся к назначенной задаче.** Не делать попутных рефакторингов, не форматировать чужие файлы.
9. **Сохранять целостность комментариев и документации.** Не удалять существующие TODO и архитектурные пояснения, если они не потеряли актуальность.
10. **По завершении шага формировать обязательный итоговый отчёт**: список изменённых файлов, результаты тестов, выявленные ограничения и следующий рекомендуемый шаг.

## 5. Инструкции по этапам работ

### Для агентов Этапа A (Точные планировки)
- **Главный документ**: [docs/GEOMETRY_SPEC.md](docs/GEOMETRY_SPEC.md) и [docs/IMPLEMENTATION_PLAN.md § Этап A](docs/IMPLEMENTATION_PLAN.md#этап-a-точные-планировки-помещений).
- Не начинайте массовый импорт до завершения пилотного этажа (задача A6) и подтверждения человеком!
- Всегда проводите калибровку чертежа с контрольными отрезками (ошибка масштаба `< 1%`).
- Ни при каких обстоятельствах не искажайте внутренние размеры комнат ради совмещения со спутниковым контуром ([ADR-010](docs/DECISIONS.md#adr-010-запрет-неявного-масштабирования-внутренней-геометрии)).
- Сохраняйте существующие идентификаторы помещений через таблицу алиасов `legacyIds`.
- Для каждого этажа создавайте отчёт импорта в `docs/import-reports/<floorId>.md`.

### Для агентов Этапа B (2D Edit Mode)
- **Главный документ**: [docs/IMPLEMENTATION_PLAN.md § Этап B](docs/IMPLEMENTATION_PLAN.md#этап-b-2d-edit-mode-режим-редактирования-карты) и [docs/GEOMETRY_SPEC.md §6](docs/GEOMETRY_SPEC.md#6-изменение-пропорций-здания-без-искажения-интерьера-proposed).
- Редактор обязан работать поверх той же модели данных, что и 3D-сцена (`CampusDocument` v1). Запрещено делать отдельный формат для 2D!
- Все мутации данных — строго через `Command Pattern` в `DocumentStore` с поддержкой `undo` и `redo`.
- Редактирование геометрии здания не должно ломать относительные размеры внутренних комнат.
- Любое сохранение должно проходить валидацию `validateDocument()`.

### Для агентов Этапа C (Визуальное улучшение)
- **Главный документ**: [docs/IMPLEMENTATION_PLAN.md § Этап C](docs/IMPLEMENTATION_PLAN.md#этап-c-визуальное-улучшение).
- Не приступайте к этапу C, пока геометрия не стабилизирована.
- Все ассеты (HDRI, текстуры, геометрия) должны быть локализованы в `public/assets/`; внешние ссылки на CDN запрещены ([ADR-018](docs/DECISIONS.md#adr-018-локализация-всех-3d-ассетов-и-отказ-от-внешних-cdn)).
- Избавьтесь от хардкодных `switch(building.id)` в `DetailedBuilding.tsx` через структуры `appearance` в данных ([ADR-015](docs/DECISIONS.md#adr-015-перевод-визуальных-стилей-зданий-из-кода-в-данные-конфигурации)).
- Растительность должна быть детерминированной (фиксированный seed) и не пересекать дороги и строения.
- Обязателен замер производительности: не более 100 Draw Calls на общий вид кампуса.

## 6. Правила проверки и тестирования

Перед завершением любой задачи агент обязан выполнить:
1. `npm run typecheck` — отсутствие ошибок компиляции TypeScript.
2. `npm test` — все юнит-тесты должны проходить успешно.
3. Проверку git-статуса: отсутствие временных файлов, артефактов сборки и случайных изменений.
4. Валидацию данных (если изменялись файлы геометрии) через модуль валидации.
